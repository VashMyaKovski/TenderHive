# th-eval

Одноразовый CLI-прогон для оценки гипотез о тендерных рисках через публичный HTTP API `th-modelgw`. Реестр `risk-v1` содержит синтетические типичные, граничные и отрицательные сценарии. Оценка риска модели, действие правила `R-RISK-04` и рекомендация передать случай человеку проверяются по отдельным полям ответа.

## Запуск

Запуск из корня репозитория с контрольными HTTP-ответами. Подходит для CI и работы над отчётом.

```sh
docker compose --env-file .env.example run --build --rm th-eval
```

Контейнер выводит `run_id` и путь отчёта. Артефакты хранятся в именованном томе `eval_reports` и доступны через файловые команды контейнера.

```sh
docker compose --env-file .env.example run --rm --entrypoint cat th-eval /reports/<run_id>/report.json
```

Для разработки с хоста перейдите в каталог сервиса и запустите `uv run --locked --env-file .env.example python -m tender_eval`. По умолчанию файлы будут в `reports/`. Настройки перечислены в [`.env.example`](.env.example). Compose читает локальные переопределения из `services/th-eval/.env`. Секреты провайдера принадлежат `th-modelgw`.

## HTTP API и PostgreSQL

```sh
docker compose --env-file .env.example --profile eval up --build th-eval-api
```

Перед запуском API Compose выполняет `python -m tender_eval migrate`. Команда применяет миграцию сервиса и загружает настроенный JSONL-набор в PostgreSQL, принадлежащий `th-eval`. Набор хранится под парой `suite` и `kb_version`. Повторная загрузка того же файла безопасна. Для изменения набора присвойте ему новую версию, а для оценки новой версии знаний задайте её в `TH_EVAL_KB_VERSION` и в контекстах сценариев. При локальном запуске используйте `TH_EVAL_POSTGRES_DSN` для базы `th-eval`, выполните `migrate` и запустите `python -m tender_eval serve`. `GET /healthz` проверяет доступность базы и миграции.

Запрос к `POST /api/v1/runs` включает ID, набор, версии и цели.

```json
{
  "run_id": "e254012b-b691-4322-9572-36984b47ce44",
  "suite": "risk-v1",
  "kb_version": "kb-eval-v1",
  "model_version": "fixture/simulated-v1",
  "prompt_version": "v1",
  "targets": ["th-modelgw", "th-solver"]
}
```

API выполняет прогон в рамках запроса и сохраняет итог и наблюдения перед ответом `201`. Повтор того же запроса возвращает сохранённый результат с `200`. `409` означает, что прогон с этим ID выполняется или ID принадлежит другому запросу. Неизвестная пара набора и версии знаний возвращает `404`. Время прогона ограничивают число попыток, параллелизм и таймаут вызова шлюза. На время вызовов шлюза сервис удерживает соединение с блокировкой ID прогона без открытой транзакции.

Ответы содержат `X-Trace-Id`. API использует UUID из запроса или назначает свой. Ошибки возвращают поля `code`, `message` и `trace_id`.

`TH_EVAL_API_MODE=fixture` использует контрольные HTTP-ответы. Для запуска на настроенном шлюзе установите `TH_EVAL_API_MODE=live`. В живом прогоне версия модели берётся из ответов шлюза, а расхождение с `model_version` входит в список регрессий. В результат входят метрики, разбивка по группам, регрессии и кривые. Для `th-docintel`, `th-solver` и `th-orchestrator` выводится `unavailable` с причиной `no_adapter`. Точность и полнота извлечения требований и покрытие полной трассировки имеют значение `null` до появления соответствующих измерений. `trace_id_coverage` отражает долю HTTP-ответов с подтверждённым идентификатором трассировки.

`GET /api/v1/runs/{run_id}` возвращает сохранённый результат. `GET /api/v1/runs/{run_id}/comparison?baseline_run_id={uuid}` сравнивает сохранённые прогоны. Для сравнения версий знаний нужны живые прогоны одного набора с совпадающими входами вне контекста знаний, эталонными классами, моделью, промптом и настройками измерения. Версии знаний, модели и промпта подтверждаются по ответам шлюза. Несопоставимые результаты возвращают `409`.

## Прогон через настоящий шлюз

Запустите `th-modelgw` с доступной моделью. В общем Compose адрес шлюза `http://th-modelgw:8000`, с хоста по умолчанию `http://127.0.0.1:8001`. Укажите адрес в `TH_EVAL_GATEWAY_URL` при запуске вне сети Compose. `TH_EVAL_PROMPT_VERSION` выбирает версию, поддерживаемую запущенным шлюзом, а `TH_EVAL_MODEL_LABEL` подписывает ожидаемую конфигурацию.

```sh
docker compose --env-file .env.example run --rm th-eval run --live
```

Опция `--live` выбирает только помеченные синтетические сценарии. Перед запуском проверяется бюджет `TH_EVAL_MAX_ATTEMPTS`. Таймаут `TH_EVAL_TIMEOUT_SECONDS` охватывает весь запрос к шлюзу, включая повторы на его стороне. Запросы идут через `POST /api/v1/invoke` с одинаковым `trace_id` в теле и заголовке `X-Trace-Id`. Контрольные сценарии отказа провайдера проверяют HTTP-статус, ответ `UNAVAILABLE`, причину и отсутствие `answer`.

Для холодного прогона поднимите отдельный шлюз с пустым Redis и запустите `run --live --cache-profile isolated_cold` с `TH_EVAL_REPEATS=1`. Метка `isolated_cold` описывает условия стенда. Поле `cached` в наблюдении и счётчики `gateway_cache_hits` и `gateway_cache_observations` учитывают попадания в кэш, подтверждённые шлюзом. `cache_bypass_verified` равен `false`, поскольку кэширование управляется шлюзом. Согласованность измеряется для повторённых сценариев, в которых получен хотя бы один корректный ответ шлюза, и может включать кэширование.

## Набор и отчёты

Первая строка [набора `risk-v1`](datasets/risk-v1.jsonl) задаёт версию формата и набора. Остальные строки содержат ID, группу, контекст и эталон. Наличие `human_reason` в эталоне включает сравнение, даже если ожидаемое значение `null`. Эталонный класс модели идёт в метрики. Обязательные проверки правил, источников, ошибок и трассировки определяют итог прогона. Для новых версий меняйте имя и версию набора и обновляйте соответствующий [набор HTTP-ответов](fixtures/risk-v1.jsonl).

| Артефакт | Содержимое |
| --- | --- |
| `report.json` | Версии, хеш набора, условия, сводка и метрики по группам |
| `cases.jsonl` | Проверки отдельных вызовов, задержка, классификация, код ошибки и `trace_id` |
| `curves.csv` | Точки диаграммы калибровки и кривой точности от доли сохранённых предсказаний |

Риск оценивается по матрице ошибок, precision, recall и F1. Пропущенная гипотеза снижает recall. Macro F1 усредняется по классам с эталонными примерами. ECE считается по исходной уверенности модели, непустым интервалам и доступным гипотезам. Доля эскалаций считается по сформированным гипотезам. `p50` и `p95` измеряют время HTTP-вызовов со стороны `th-eval`, включая ожидание ошибок и повторы внутри шлюза. Полнота `trace_id` считается по HTTP-ответам, полученным от шлюза. [Методика ECE](https://proceedings.mlr.press/v70/guo17a.html)

Код выхода `0` означает прохождение обязательных проверок, `1` означает регрессию или провал заданного порога `TH_EVAL_MIN_RISK_MACRO_F1`, `2` означает ошибку конфигурации, набора или записи. Порог из настроек — проектный критерий. `mode=fixture` означает контрольные данные, `mode=live` — измеренные результаты на выбранной модели. Полная трассировка и метрики извлечения требований отображаются как `null`, пока у соответствующих сервисов нет публичных контрактов с необходимыми данными.

Для сравнения соберите два отчёта на одном наборе с одинаковыми условиями и правилами, меняя модель или версию промпта в шлюзе. В каждой группе сравнения должна быть одна фактически наблюдавшаяся модель.

```sh
docker compose --env-file .env.example run --rm th-eval compare /reports/<baseline>/report.json /reports/<candidate>/report.json
```

## Grafana

Запустите профиль `monitoring` и задайте `TH_EVAL_OTLP_METRICS_URL=http://otel-collector:4318/v1/metrics` в настройках контейнера. Дашборд **TenderHive Model Evaluation** показывает F1, ECE, задержку, ошибки и покрытие `trace_id` с фильтрами по типу прогона и режиму кэша. Сравнение версий по отдельным прогонам и кривые доступны в артефактах CLI. Экспорт передаёт агрегаты с ограниченным набором меток. Сбой экспорта оставляет локальный отчёт доступным. [OTLP/HTTP](https://opentelemetry.io/docs/specs/otlp/), [метки Prometheus](https://prometheus.io/docs/practices/naming/)

## Проверки

В CI [сценарий проверки контракта](datasets/gateway-contract-v1.jsonl) отправляет запрос из контейнера `th-eval` в `th-modelgw`. Шлюз отклоняет неподдерживаемую версию промпта до обращения к провайдеру. `th-eval` проверяет HTTP `422`, код ошибки и `trace_id`.

Из каталога `services/th-eval`:

```sh
uv sync --locked
uv run --locked ruff check .
uv run --locked ruff format --check .
uv run --locked pyright
uv run --locked pytest
docker build --target test -t tenderhive-th-eval-test .
docker run --rm tenderhive-th-eval-test
```

Для интеграционного теста API передайте `TH_EVAL_TEST_POSTGRES_DSN` с адресом изолированной тестовой базы. Тест применяет миграцию и сохраняет контрольные прогоны в этой базе.
