# th-eval

Одноразовый CLI-прогон для оценки гипотез о тендерных рисках через публичный HTTP API `th-modelgw`. Реестр `risk-v1` содержит синтетические типичные, граничные и отрицательные сценарии. Оценка риска модели, действие правила `R-RISK-04` и рекомендация передать случай человеку проверяются по отдельным полям ответа.

## Запуск

Запуск из корня репозитория с контрольными HTTP-ответами. Подходит для CI и работы над отчётом.

```sh
docker compose --env-file .env.example run --build --rm th-eval
```

Контейнер выводит `run_id` и путь отчёта. Артефакты хранятся в именованном томе `eval_reports` и доступны через файловые команды контейнера.

```sh
docker compose --env-file .env.example run --rm --entrypoint cat th-eval /reports/<run_id>/report.json
```

Для разработки с хоста перейдите в каталог сервиса и запустите `uv run --locked --env-file .env.example python -m tender_eval`. По умолчанию файлы будут в `reports/`. Настройки перечислены в [`.env.example`](.env.example). Compose читает локальные переопределения из `services/th-eval/.env`. Секреты провайдера принадлежат `th-modelgw`.

## Прогон через настоящий шлюз

Запустите `th-modelgw` с доступной моделью и укажите его адрес в `TH_EVAL_GATEWAY_URL`. В общем Compose адрес `http://th-modelgw:8000`, с хоста по умолчанию `http://127.0.0.1:8001`. Пока ветки интегрируются отдельно, можно запустить шлюз из его рабочей копии и запускать `th-eval` с хоста. `TH_EVAL_PROMPT_VERSION` выбирает версию, поддерживаемую запущенным шлюзом, а `TH_EVAL_MODEL_LABEL` подписывает ожидаемую конфигурацию.

```sh
docker compose --env-file .env.example run --rm th-eval run --live
```

Опция `--live` выбирает только помеченные синтетические сценарии. Перед запуском проверяется бюджет `TH_EVAL_MAX_ATTEMPTS`. Таймаут `TH_EVAL_TIMEOUT_SECONDS` охватывает весь запрос к шлюзу, включая повторы на его стороне. Контрольные сценарии отказа провайдера ожидают код ошибки и отсутствие `answer`. Такой отказ считается корректным исходом эталонного случая.

Для холодного прогона поднимите отдельный шлюз с пустым Redis и запустите `run --live --cache-profile isolated_cold` с `TH_EVAL_REPEATS=1`. Метка `isolated_cold` описывает условия стенда. Публичный ответ шлюза пока не подтверждает попадание в кэш или его обход, поэтому `cache_bypass_verified` равен `false`. Для повторных прогонов в текущем контракте согласованность относится к ответам шлюза и может включать кэширование.

## Набор и отчёты

Первая строка [набора `risk-v1`](datasets/risk-v1.jsonl) задаёт версию формата и набора. Остальные строки содержат ID, группу, контекст и эталон. Наличие `human_reason` в эталоне включает сравнение, даже если ожидаемое значение `null`. Эталонный класс модели идёт в метрики. Обязательные проверки правил, источников, ошибок и трассировки определяют итог прогона. Для новых версий меняйте имя и версию набора и обновляйте соответствующий [набор HTTP-ответов](fixtures/risk-v1.jsonl).

| Артефакт | Содержимое |
| --- | --- |
| `report.json` | Версии, хеш набора, условия, сводка и метрики по группам |
| `cases.jsonl` | Проверки отдельных вызовов, задержка, классификация, код ошибки и `trace_id` |
| `curves.csv` | Точки диаграммы калибровки и кривой точности от доли сохранённых предсказаний |

Риск оценивается по матрице ошибок, precision, recall и F1. Пропущенная гипотеза снижает recall. Macro F1 усредняется по классам с эталонными примерами. ECE считается по исходной уверенности модели, непустым интервалам и доступным гипотезам. Доля эскалаций считается по сформированным гипотезам. `p50` и `p95` измеряют время HTTP-вызовов со стороны `th-eval`, включая ожидание ошибок и повторы внутри шлюза. Полнота `trace_id` считается по HTTP-ответам, полученным от шлюза. [Методика ECE](https://proceedings.mlr.press/v70/guo17a.html)

Код выхода `0` означает прохождение обязательных проверок, `1` означает регрессию или провал заданного порога `TH_EVAL_MIN_RISK_MACRO_F1`, `2` означает ошибку конфигурации, набора или записи. Порог из настроек — проектный критерий. `mode=fixture` означает контрольные данные, `mode=live` — измеренные результаты на выбранной модели. Полная трассировка и метрики извлечения требований отображаются как `null`, пока у соответствующих сервисов нет публичных контрактов с необходимыми данными.

Для сравнения соберите два отчёта на одном наборе с одинаковыми условиями и правилами, меняя модель или версию промпта в шлюзе. В каждой группе сравнения должна быть одна фактически наблюдавшаяся модель.

```sh
docker compose --env-file .env.example run --rm th-eval compare /reports/<baseline>/report.json /reports/<candidate>/report.json
```

## Grafana

Запустите профиль `monitoring` и задайте `TH_EVAL_OTLP_METRICS_URL=http://otel-collector:4318/v1/metrics` в настройках контейнера. Дашборд **TenderHive Model Evaluation** показывает F1, ECE, задержку, ошибки и покрытие `trace_id` с фильтрами по типу прогона и режиму кэша. Сравнение версий по отдельным прогонам и кривые доступны в артефактах CLI. Экспорт передаёт агрегаты с ограниченным набором меток. Сбой экспорта оставляет локальный отчёт доступным. [OTLP/HTTP](https://opentelemetry.io/docs/specs/otlp/), [метки Prometheus](https://prometheus.io/docs/practices/naming/)
