# Разработка TenderHive

1. Создайте рабочую ветку от актуальной `dev`, например `feat/th-kb-import`.
2. Открывайте PR в `dev`. В описании укажите затронутые сервисы, изменения API, событий, миграций или переменных окружения и результаты проверок.
3. Попросите ревью у владельца сервиса. Изменения в `contracts/` заранее согласуйте с командами производителей и потребителей. Для новой схемы сообщения согласуйте версию, совместимость, ключ партиции и обработку повторной доставки.
4. Перед слиянием выполните [общие проверки](README.md#проверки) и проверки изменённых сервисов. Изменения зависимостей включают `pyproject.toml` и соответствующий `uv.lock`.

## Как добавить Python-сервис

- Создайте каталог `services/<имя-сервиса>/` по [карте ответственности](services/README.md). Ведите README, зависимости, lock-файл, тесты, миграции и Dockerfile внутри сервиса.
- Используйте Python 3.14, FastAPI для REST, Pydantic v2 для входных и выходных схем. Отделяйте транспорт и I/O от бизнес-правил. Соседние сервисы вызывайте через публичные API и события Kafka. `contracts/` предназначен для обмена данными между сервисами.
- Опишите обязательные настройки через `pydantic-settings.BaseSettings` и добавьте безопасный `.env.example`. Передавайте настройки и адаптеры явно при сборке приложения. Для внешних вызовов задавайте таймауты и закрывайте клиенты при остановке.
- Добавьте юнит- и интеграционные тесты по потребности сервиса. Подключите их к CI вместе с Ruff и Pyright в окружении самого сервиса. Корневые pytest и Pyright сейчас проверяют общие контракты и их тесты.
- Для контейнера используйте Python 3.14, устанавливайте зависимости из lock-файла, запускайте приложение от непривилегированного пользователя и добавьте проверку готовности. Если контекст сборки указывает на каталог сервиса, добавьте `.dockerignore` в этот каталог.
